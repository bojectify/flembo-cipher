# Contributing to flembo-cipher

Thanks for helping. This guide covers building and testing the project, how
changes get merged, and how releases are made.

For what the tool does and how to use it, see the [README](README.md).

## Setup

You'll need [Rust](https://rustup.rs) (edition 2024).

```bash
git clone https://github.com/bojectify/flembo-cipher.git
cd flembo-cipher
cargo build
cargo run -- "Hello, world!" --seed 42
```

## Before opening a pull request

All three of these should pass:

```bash
cargo test                    # unit tests
cargo clippy --all-targets    # lint, with no warnings
cargo fmt --check             # formatting
```

- **Formatting:** the project uses 2-space indentation (see `rustfmt.toml`).
  Run `cargo fmt` to fix formatting automatically.
- **Tests:** new behaviour needs tests, and bug fixes need a test that fails
  without the fix. Tests live next to the code, in a `#[cfg(test)] mod tests`
  at the bottom of each file.
- **Randomness in tests:** use a seeded generator
  (`StdRng::seed_from_u64(...)`) so results are repeatable. Where possible, test
  logic with hand-built inputs instead of random ones.
- **Behaviour changes:** if a change affects the output, the cleaning rules or
  the errors, update the README to match. Programs that call this tool rely on
  it.

## Project layout

| File | Responsibility |
| --- | --- |
| `src/main.rs` | Argument parsing, error output and exit codes, printing JSON |
| `src/phrase.rs` | Validating and cleaning the phrase |
| `src/mapping.rs` | Building the random letter mapping |
| `src/cipher.rs` | Applying the mapping and building the key |
| `dist-workspace.toml` | Release configuration for [dist](https://opensource.axo.dev/cargo-dist/) |
| `.github/workflows/release.yml` | Release workflow, generated by dist. Don't edit by hand. |

## How changes get merged

- `main` is protected. All changes go through a pull request, including the
  maintainer's.
- For pull requests from forks, a maintainer has to approve the workflow run
  before checks start.
- The `Release` workflow runs `dist plan` on every pull request as a check. It
  doesn't build or publish anything.

## Releasing (maintainers)

Releases are built and published by GitHub Actions when a version tag is
pushed. Pushing tags is restricted to repository admins.

1. **Bump the version** in `Cargo.toml` (e.g. `0.1.0` → `0.2.0`) and run
   `cargo build` so `Cargo.lock` updates. Merge that change through a pull request.
2. **Tag the merged commit and push the tag.** The tag must match the version in
   `Cargo.toml`:
   ```bash
   git switch main && git pull
   git tag v0.2.0
   git push origin v0.2.0
   ```
3. **Watch the `Release` workflow** in the Actions tab. It takes about 5–10
   minutes and:
   - builds binaries for macOS (Apple Silicon and Intel), Linux (x86_64 and
     ARM64) and Windows
   - creates the GitHub Release with the binaries, checksums, and shell and
     PowerShell installers
   - pushes the updated formula to
     [`bojectify/homebrew-tap`](https://github.com/bojectify/homebrew-tap)
4. **Check it:** `brew upgrade flembo-cipher && flembo-cipher --version`.

If any build fails, nothing is published, so you can fix the problem and move
the tag to the fixed commit:

```bash
git push --delete origin v0.2.0
git tag -f v0.2.0
git push origin v0.2.0
```

If only the Homebrew step fails, the GitHub Release is already live. Fix the
cause and re-run just the failed jobs from the Actions tab (or
`gh run rerun <run-id> --failed`). Don't create a new tag.

### Changing the release setup

Edit `dist-workspace.toml`, then regenerate the workflow:

```bash
dist generate    # install with: cargo install cargo-dist --locked
```

Commit both files. Don't edit `.github/workflows/release.yml` directly, because
`dist generate` overwrites it.

### Known issues

- **Apple Silicon runner:** dist 0.32 defaults `aarch64-apple-darwin` builds to
  the `macos-14` runner image, which GitHub retires on 2 November 2026.
  `dist-workspace.toml` overrides this to `macos-15` under
  `[dist.github-custom-runners]`. If you upgrade dist, check whether the
  override is still needed.
- **Homebrew token:** the `publish-homebrew-formula` job uses the
  `HOMEBREW_TAP_TOKEN` repository secret. It's a fine-grained token owned by the
  `bojectify` organisation, with **Contents: read and write** on
  `homebrew-tap` only. When it expires, that job fails with an authentication
  error. Create a new token and update the secret:
  ```bash
  gh secret set HOMEBREW_TAP_TOKEN -R bojectify/flembo-cipher
  ```
- **Tap branch protection:** the workflow pushes directly to `homebrew-tap`'s
  `main` branch. Don't add a ruleset there that requires pull requests, or the
  Homebrew step will fail.
